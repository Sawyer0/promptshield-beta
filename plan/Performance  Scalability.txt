# PromptShield Performance & Scalability Architecture 

## Executive Summary 

PromptShield’s performance architecture enables scanning of gigabyte-scale files through 
streaming processing, intelligent parallelization, and bounded memory usage. Our CLI-first 
approach prioritizes local processing speed over network-dependent solutions, positioning us as 
the fastest LLM security scanner for development and CI/CD workflows. 

**Key Performance Targets:** 

- Process 1GB JSON files in <30 seconds on standard developer hardware 
- Maintain <500MB memory usage regardless of file size 
- Linear scaling with CPU cores for multi-file processing 
- Sub-second response for files <1MB 

## Core Architecture Principles 

### 1. Streaming-First Design 

Never load entire files into memory. All processing uses bounded buffers and streaming parsers 
to maintain predictable resource usage. 

### 2. Progressive Feedback 

Users see results as they’re discovered, not after complete processing. This builds confidence 
during long operations and enables early termination on critical findings. 

### 3. Configurable Performance Profiles 

Developers can optimize for speed, thoroughness, or resource constraints based on their 
specific environment and requirements. 

## Technical Architecture 

### Streaming Processing Pipeline 

``` 
Input → Tokenizer → Pre-filter → Rule Engine → Aggregator → Output 
  ↓         ↓           ↓            ↓            ↓          ↓ 
Stream   Bounded    Bloom Filter  Parallel    Priority    Progressive 
Reader   Buffer     + Keywords    Matching     Queue       Reporter 
``` 

 
 
 
 
 
 
 
 
 
 
 
 
 
 
 
Each stage operates independently with channels providing backpressure control. This 
architecture ensures: 

- Maximum memory usage is deterministic 
- Early detection enables fast-fail scenarios 
- Natural integration with Unix pipes and CI/CD tools 

### Memory Management Strategy 

#### Three-Tier Memory Model 

**Tier 1: Working Memory (Default 128MB)** 

- Active processing buffers 
- Compiled regex cache 
- Rule engine state 

**Tier 2: Cache Memory (Default 256MB)** 

- Recently evaluated patterns 
- LRU finding deduplication 
- Temporary result storage 

**Tier 3: Spill-to-Disk (Automatic)** 

- Findings exceeding memory limits 
- Large intermediate results 
- Memory-mapped file access 

#### Configuration Options 

```yaml 
performance: 
  max_memory: 512MB      # Hard limit for total usage 
  buffer_size: 8MB       # Per-file streaming buffer 
  cache_size: 256MB      # Pattern and result caching 
  enable_mmap: true      # Memory-mapped file support 
  low_memory_mode: false # Aggressive memory optimization 
``` 

### Parallelization Strategy 

#### File-Level Parallelism 

 
 
 
 
 
 
 
 
 
 
 
 
 
 
**Adaptive Worker Pool:** 

- Default: `runtime.NumCPU()` workers 
- Monitors system load and adjusts dynamically 
- Prioritizes small files for quick feedback 
- Maintains deterministic output ordering 

**Smart Scheduling Algorithm:** 

1. Sort files by size (ascending) 
1. Process small files first for immediate feedback 
1. Distribute large files across available workers 
1. Merge results maintaining original order 

#### Intra-File Parallelism 

For files >100MB, we partition at natural boundaries: 

**JSON Arrays:** Split on array elements 
**JSONL/Logs:** Split on line boundaries   
**Nested JSON:** Split on top-level objects 

Each partition processes independently with configurable overlap for context-dependent rules. 

## Performance Optimization Strategies 

### Rule Engine Optimizations 

#### Pattern Matching Hierarchy 

1. **Bloom Filters** (Nanoseconds) 
- Quick negative filtering 
- Eliminates 90%+ of non-matches 
- Negligible memory overhead 
1. **Keyword Indexing** (Microseconds) 
- Trie-based keyword matching 
- Early termination on matches 
- Shared across rules 
1. **Regex Evaluation** (Milliseconds) 
- Compiled pattern cache 
- SIMD acceleration where available 
- Lazy evaluation on demand 
1. **LLM Semantic Analysis** (Seconds) 
- Only for high-confidence threats 

 
 
 
 
 
 
 
 
 
 
 
- Batched API calls 
- Response caching 

### File Type Specific Optimizations 

#### JSON/JSONL Files 

**SAX-Style Parsing:** 

- Event-driven processing without DOM construction 
- Path-based filtering for targeted scanning 
- Lazy number/string parsing 

**Implementation:** 

```go 
scanner := NewJSONScanner(reader) 
scanner.OnPath("$.users[*].email", checkPII) 
scanner.OnPath("$.messages[*].content", checkInjection) 
scanner.Stream() // Processes without loading full file 
``` 

#### Log Files 

**Line-Based Streaming:** 

- Configurable look-ahead/behind windows 
- Pattern-based line aggregation 
- Automatic format detection 

#### Binary/Encoded Data 

**Smart Detection:** 

- Magic byte identification 
- Automatic encoding detection 
- Base64/hex decoding on-demand 
- Clear unsupported format messages
