## Our Foundational Approach: Progressive Security Architecture 

The research revealed something crucial: most CLI tools fail because they either start too 
complex (overwhelming developers) or start too simple (can’t scale to enterprise). Our solution 
follows what I call “progressive security architecture” - we implement enterprise-grade security 
foundations from day one, but expose complexity gradually as users and organizations mature. 

Here’s how this works in practice. When a developer first installs PromptShield, they get a 
beautifully simple experience - `promptshield login` opens their browser, they authenticate once, 
and everything just works. Behind the scenes, we’re implementing OAuth 2.0 with PKCE, 
storing credentials in OS keychains, and setting up audit logging. The developer doesn’t need to 
understand any of this complexity, but we’ve built the foundation for enterprise features they’ll 
eventually need. 

## Layer 1: Credential Management (MVP Foundation) 

Our credential architecture starts with what the research showed as absolutely critical - 
OS-native secure storage with proper fallback mechanisms. Let me explain the reasoning 
behind each decision. 

We implement a credential hierarchy that checks environment variables first (for CI/CD), then 
OS keychain storage (for developer machines), then interactive prompts as fallback. This 
pattern handles every deployment scenario while maintaining security. The AWS CLI gets this 
right, and we follow their model but improve the user experience. 

For API key storage, we use a hybrid approach. LLM provider keys (OpenAI, Anthropic) get 
stored in OS keychains with service-specific namespacing. This means your OpenAI key for 
PromptShield never conflicts with keys from other tools, and we can rotate or revoke them 
independently. Our own platform authentication tokens use shorter expiration periods with 
automatic refresh, following the OAuth 2.0 pattern. 

The critical insight from the research is that credential compromise happens most often during 
storage, not transmission. By using macOS Keychain, Windows Credential Manager, and Linux 
Secret Service API, we delegate encryption to battle-tested, OS-level systems rather than rolling 
our own crypto. 

## Layer 2: Authentication Flows (CLI to Platform Bridge) 

This is where our architecture gets sophisticated while remaining developer-friendly. We 
implement OAuth 2.0 device authorization grant as our primary authentication method because 
the research showed this has become the de facto standard for CLI tools. 

Here’s how a developer experiences this: they run `promptshield login`, we display a short code 
and open their browser to our authentication page. They enter the code, authenticate with their 

 
 
 
 
 
 
 
 
 
 
preferred method (GitHub, Google, or email), and we securely receive the tokens without any 
credential handling in the CLI itself. The entire flow takes under 30 seconds and feels magical to 
users. 

Behind the scenes, we’re implementing RFC 8628 with PKCE extensions, using 
cryptographically secure random code generation, and handling all the edge cases the research 
identified - network timeouts, browser compatibility, headless environments. We also support 
organization-specific authentication flows, so enterprises can integrate with their existing identity 
providers. 

The beautiful aspect of this design is that it naturally bridges from individual developer usage to 
team and enterprise scenarios. When a developer joins an organization using PromptShield, 
their existing authentication just works, but they automatically inherit organizational policies and 
permissions. 

## Layer 3: Permission Model (Team and Enterprise Ready) 

Our permission architecture draws heavily from GitHub’s fine-grained access control model, 
which the research showed as the current gold standard. We implement what I call “contextual 
permissions” - your access level depends on what you’re scanning, where you’re scanning it, 
and what organization context you’re operating in. 

Let me illustrate with a concrete example. A developer scanning their local project files has full 
access to all security rules and can see detailed findings. When they’re scanning on behalf of 
their organization, they might have restricted access to certain compliance rule packs, and their 
scan results automatically flow to the organization’s security dashboard. If they’re running scans 
in CI/CD, they operate under service account permissions with narrowly scoped access. 

This model scales naturally from individual use to enterprise deployment. Individual developers 
start with full personal access. Teams get shared rule packs and collaborative features. 
Organizations get centralized policy management, audit trails, and compliance reporting. Each 
level builds on the previous one without breaking existing workflows. 

## Layer 4: Audit and Compliance Architecture 

The research made it clear that audit logging isn’t optional in 2025 - it’s a fundamental 
requirement for any security tool. Our approach implements comprehensive audit trails from day 
one, but we make them invisible to individual developers and increasingly valuable as 
organizations mature. 

Every scan operation generates structured audit events that include the user identity, scan 
parameters, findings summary, and organizational context. We use JSON formatting with 
OpenTelemetry compatibility, ensuring integration with existing security monitoring tools. For 

 
 
 
 
 
 
 
 
 
individual developers, these logs remain local and private. For teams and enterprises, logs flow 
to centralized systems with tamper-evident storage. 

The key architectural decision here is implementing privacy by design. We log security-relevant 
events without storing sensitive content from scanned files. This gives us forensic capabilities 
while respecting developer privacy and meeting compliance requirements like GDPR and 
HIPAA. 

## Layer 5: Compliance Framework Integration 

This is where our research really pays off. Instead of bolting on compliance features later, we 
design our entire architecture to support SOC 2, HIPAA, and GDPR requirements from the 
foundation up. 

Our data handling follows strict minimization principles - we only collect what’s necessary for 
security analysis and retain it only as long as required. API calls to LLM providers use our own 
encryption layer on top of TLS, ensuring sensitive prompts remain protected even if transport 
security fails. All cross-border data transfers implement Standard Contractual Clauses and data 
residency controls. 

For enterprises, we provide compliance dashboards that show real-time adherence to security 
policies, audit log completeness, and regulatory requirements. This transforms compliance from 
a periodic burden into continuous assurance. 

## Implementation Strategy: Phased Rollout 

The beautiful aspect of this architecture is that we can implement it progressively without 
disrupting the developer experience. Phase one focuses on the credential management and 
basic authentication flows - this gives us a secure foundation with minimal complexity. Phase 
two adds team features and organizational permissions. Phase three implements advanced 
compliance and enterprise integration capabilities. 

Each phase builds naturally on the previous one. A developer who starts using PromptShield 
individually can seamlessly transition to team usage and eventually enterprise deployment 
without changing their daily workflow. The complexity scales with organizational needs rather 
than overwhelming individual users. 

## Platform Evolution Path 

This authentication and security model naturally supports our evolution from CLI tool to 
comprehensive platform. The device flow authentication works identically for CLI access and 
web dashboard usage. The permission model scales from individual rule packs to organizational 
policy management. The audit framework supports both command-line operations and 
web-based administration. 

 
 
 
 
 
 
 
 
 
 
When we launch our marketplace for security rule packs, the authentication system already 
handles publisher verification, user authorization, and organizational approval workflows. When 
we add real-time scanning APIs, the credential management system supports service accounts 
and API key rotation. When enterprises need custom compliance reporting, our audit framework 
already captures the necessary events. 

## Why This Solution Works 

The research showed that successful CLI security tools share three characteristics: they start 
simple but scale elegantly, they integrate with existing developer workflows rather than 
disrupting them, and they provide enterprise capabilities without overwhelming individual users. 

Our progressive security architecture achieves all three objectives. We provide enterprise-grade 
security from day one, but we expose complexity only when users need it. We follow established 
patterns from successful tools like GitHub CLI and AWS CLI, but we improve the user 
experience and add capabilities specific to security scanning workflows. 

Most importantly, this architecture positions PromptShield for long-term success. As the security 
landscape evolves and compliance requirements increase, we have the foundation to adapt 
quickly without breaking existing user workflows or requiring architectural rewrites. 

The result is an authentication and security model that feels magical to individual developers, 
scales effortlessly to enterprise requirements, and provides the compliance capabilities that will 
make PromptShield indispensable to security-conscious organizations. This is how we build the 
“ESLint for LLMs” - by creating security tooling that developers actually want to use while 
meeting the enterprise requirements that drive sustainable business growth.
